# 编排固定工作流 + 项目经理汇报模式 设计（v1）

- 日期：2026-09-28
- 状态：**定稿**（用户确认：固定模板、节点不预填、项目经理汇报、无人值守、动态可视化、**工作目录必填 + OpenCode 项目下拉**）；作为「集群功能 v1」一次性实施与交付
- 关联：[cluster-architecture.md](../../cluster-architecture.md)（P0–P2 基线）、PR #64（手动开始+节点预览+汇报回注）、#65（OpenCode 会话映射）、#66（service.rs 拆分）、#68（投递可靠性）、#69（模板内核）、#70（权限无人值守）
- 术语：**模板**（固定的流程定义）/ **节点**（模板里的一步）/ **首节点**（项目经理）/ **编排会话**（`task-<task_id>-step-<n>`）

## 0. 背景与决策脉络

真机验收暴露的问题：默认工作流直接派活、节点不可见、汇报回不来（OpenCode 会话 id 不匹配）、无人应答的选择框会卡流程。用户对交互模型的最终决策：

1. **先有工作流，再有任务**：任务创建时必须选择一条工作流；
2. **不做自由工作流编辑器**：流程/节点/角色固定成三档精选模板（公开资料选型，见 §1）；
3. **每节点 Agent + 模型可调，但都不预填**（避免系统"悄悄替我选了"——默认 codex 失败是前车之鉴）；
4. **项目经理模式**：只有首节点向人汇报，其余节点不接触人；
5. **无人值守**：编排会话不弹权限选择框（否则流程会卡死）；
6. **可视化用动态效果**，不用符号徽标。

## 1. 选型依据（公开资料）

| 来源 | 结论 | 对本文档的影响 |
| --- | --- | --- |
| Anthropic《Building effective agents》/《多代理研究系统》(2025) | 主流多代理用 **lead + 3~5 子代理**；明确"**编程类任务不适合多代理**（可并行部分少、协调成本高）"；推荐先简单固定工作流（生成者-评估者循环） | 节点数控制在 2–4；默认模板含"复核"节点（评估者角色） |
| Google DeepMind《Towards a Science of Scaling Agent Systems》(arXiv 2512.08296) | "**够好效应**"：单代理 >~45% 成功率后加代理变差；工具密集型任务（软件工程）协调开销惩罚最重；**集中式协调错误放大 4.4×，松散独立代理 17.2×** | 支持"首节点集中协调 + 集中验证"的项目经理模式；不引入独立并行代理 |
| Cognition《Don't Build Multi-Agents》(2025) | 编程场景单线程代理最可靠；多代理唯一稳妥用法 = **生成者 + 独立复核**（2 角色） | 二节点模板 = 实施→复核；中间节点产出以"汇总报告"形式回流，不碎片化人机接口 |
| MetaGPT (arXiv 2308.00352) | 软件公司 SOP 用 5 角色（产品/架构/项目/工程/QA）——全套重，工程上普遍裁剪 3–4 个 | 四节点模板参考其裁剪版：判断→规划→实施→复核 |

**结论：节点数 2–4，推荐默认 3；首节点承担项目经理（集中协调 + 集中汇报）。**

## 2. 固定工作流模板（三档）

| 模板 id | 名称 | 节点（用途） | 场景 |
| --- | --- | --- | --- |
| `template-quickfix` | 快速修复 | 实施 → 复核 | 小改动、修 bug |
| `template-standard` | **标准交付（默认推荐）** | **规划 → 实施 → 复核** | 大多数任务 |
| `template-full` | 完整评估 | 判断 → 规划 → 实施 → 复核 | 复杂 / 高风险任务 |

- 节点的**用途**固定为四选一：初步判断 / 规划整理 / 实施 / 复核汇总（与现有角色枚举一致）。
- **首节点 = 项目经理**：最后收汇总、向人汇报（§4）。
- **旧预设**（`preset-requirement-to-report` 多 Agent 委托、`preset-opencode-only`）**不再对新建任务开放**，仅保留解析能力，保证已存在任务可读可推进。
- 任务创建后**锁定所选模板**（记录在任务 meta 的 `workflow_id`）；此后模板与配置的变化不影响已创建任务。

## 3. 节点配置（无预填）

- **配置位置**：设置页「编排（集群）」区（作为**新建任务的默认配置**）+ 新建任务弹窗（任务级调整，见 §3.2）。选中模板后显示节点列表，每个节点两输入：**Agent 下拉**（来自 Agent 注册表，不限制）+ **模型输入**（手填 `provider/model`，如 `anthropic/claude-sonnet-4-5`）。
- **不预填**：Agent 与模型初始均为空（设置页首次配置）。弹窗内的起点 = 设置页已保存的默认配置；未配置则为空。
  - Agent 为空：**新流程在创建时即拦下**（`orc_step_agent_missing`「第 N 步未选择 Agent：请在创建任务时为每个节点选择 Agent」，不允许创建跑不起来的任务）；旧调用方/旧任务在点「开始执行」时预检并明确报错「第 N 步未选择 Agent：请先在设置 → 编排中配置」，任务保持「待开始」（避免跑到一半才失败）。绕过 UI 直接派活时仍按现有派活失败 → blocked 语义兜底。
  - 模型为空：界面标注「不指定（由 OpenCode 用其当前默认模型）」，**不再写「默认模型」这种含糊说法**——不替用户默默决定模型。
  - 模型仅对 OpenCode 生效（v1）：选择其他 Agent 时模型输入框置灰并注明「暂不支持指定模型」。
- **存储**：settings 键 `orchestration.node_config`，值为 JSON：
  ```json
  { "template-standard": { "1": { "agent": "opencode", "model": "anthropic/claude-sonnet-4-5" } } }
  ```
  键缺省 = 该节点未配置。读取失败按未配置处理并告警（不猜测）。
- **模板定义来源**：内置（代码常量）+ 上述用户配置合并；合并结果即新建任务弹窗的默认起点与旧调用方的运行时节点定义。

### 3.1 任务创建字段（v2 增补）

- **目标**（现有）、**通知节奏**（现有）、**模板**（必选）、**工作目录**（**必填**）。
- **工作目录来源**：下拉选择 OpenCode 已知项目 + 允许手动输入路径（下拉含「手动输入」项）。
  - 数据源：OpenCode 本地数据库 `~/.local/share/opencode/opencode.db` 的 `project` 表（`worktree` = 目录、`name`、`time_active`），按最近活跃倒序；**只读**访问，失败时明确报错并退回手动输入（不猜、不静默）。
- **校验**：创建任务时校验模板存在、工作目录存在（必须是已存在的目录）、**每个节点都已选 Agent**（任务级 steps 全量提交）；「开始执行」时再次预检（工作目录仍存在）。
- **任务级绑定**：任务 meta 记录模板 id、工作目录与步骤快照；此后改设置/节点配置不影响已创建任务。

### 3.2 新建任务弹窗与「创建即锁定」（v3 修订，2026-09-29 动线重做）

- **入口**：集群页右上角「新建任务」按钮 → 弹窗（对齐渠道页「添加渠道账号」的交互语言）。
- **弹窗内容**：目标、通知节奏、模板、工作目录、**逐个节点的 Agent/模型编辑**（起点 = 设置页默认配置，可逐任务调整）。
- **提交**：`create_orc_task` payload 新增 `steps`（全量节点配置，含 Agent 与模型）——
  - 后端 `task_steps_snapshot` 校验 order/模型规则/Agent 完整性后，**创建时即写入步骤快照**（此后改设置不影响该任务；旧调用方不传 `steps` 时保持原行为，start 时才快照）；
  - 弹窗两个动作：「仅创建」（保持待开始，可再检查）与「创建并开始」（创建成功后立即派活第 1 步；派活失败只在页面顶部如实提示，任务保持待开始可重试）。
- **列表**：单卡手风琴（对齐渠道页账号列表），默认**不展开任何任务详情**；行内展示目标/状态/进度/通知节奏，阻塞任务标红并附原因。
- **详情**（点行展开）：**工作流节点链置顶**（重点展示工作流），其下是任务信息网格与操作区；状态为「待开始」时不再显示「执行中」。

## 4. 运行流（项目经理模式）

```
创建任务（弹窗选模板并逐节点确认；「创建并开始」立即派活 / 「仅创建」保持待开始）
  → 待开始 →（若选择了仅创建）开始执行
  步骤 1（首节点·项目经理）收信封干活 → 产出①（记入任务）
  步骤 2 收信封（含前序产出）干活 → 产出②
  …最后一步完成 → 不直接完成，转入「汇总中」
  回流：把 产出①…N 放进汇总信封，resume 首节点会话
  首节点产出 = 最终汇报 → 推送给人（§5）→ 任务完成
```

- **产出记录**：每次 Agent 上报（`session.completed` 自动回注链路）记录其正文到任务 meta `step_reports`（单步截断 4000 字，总量截断 12000 字；超出部分以「…（已截断）」标注）。
- **派活透传**：派活时把**该任务的工作目录**、该步**模型**、**无人值守标志**随信封传给 Agent 适配器；OpenCode 创建会话时带 `location`/`model`，同一任务后续步骤 resume 同一目录并在模型有变化时 `switchModel`。其他适配器暂不支持（忽略）。
- **回流派活**：最后一步推进后，任务状态保持 Working 且 `final_report_pending = true`（DTO 暴露 `finalizing`，供可视化显示"项目经理汇总中"）；用首节点步（`task-<id>-step-1`）的会话 resume 派"汇总汇报"信封，模板含全部 `step_reports`。
  - 新增内置占位符 `{reports}`（沿用现有 harness 模板体系，用户可在 `harness-templates.json` 覆盖；未知占位符行为不变）。
- **最终汇报**：`final_report_pending` 状态下收到首节点会话的上报 → 任务置 Completed；呈现层推送最终汇报（正文 = 首节点产出，截断 1200 字；前后缀沿用集群消息格式）。
- **手动推进**（用户点「汇报」）没有正文：该步不记产出；汇总信封对缺失步标注「（该步无正文汇报）」。
- **失败语义**（不自动重推，§4.6 原则不变）：
  - 回流派活失败 → 任务 blocked（blocked_step = 1，原因写清"汇总汇报派活失败：…"）+ 微信失败提醒；
  - 首节点汇总回合失败 → 同样 blocked 并写清原因；**用户「重新发起」后自动重新派活**（v2 修订：不再需要再点一次「发指令」）。
- **状态机影响**：不改线性 Step 语义；「汇总中」是最后一步之后的附加阶段（meta 标记 + DTO 字段），不改 A2A TaskState 映射表。

## 5. 通知规则（只听项目经理）

- **编排会话的原始完成事件一律不推微信**：桌面端 ingest 过滤——会话 id 能解析为编排会话（`task-<id>-step-<n>`）且任务确实存在于编排任务表时，不创建通知/投递（该事件只走汇报回注与产出记录）。
- 用户可见的编排消息只来自呈现层：
  - `final_only`（默认）：只推**最终项目经理汇报**；
  - `verbose`：额外推各步的系统进度文案（不是中间节点原话）；
  - 失败提醒不受模式限制（现有语义保持）。
- 普通 OpenCode 会话（用户日常对话）通知行为完全不变。

## 6. 权限无人值守（不弹选择框）

- 插件注册 `ctx.permission.hook("evaluate")`：**仅对编排会话**把 `ask` 改为 `allow`；显式配置的 `deny` 仍然优先（hook 不改 deny）。
- 开关：`orchestration.unattended`（bool，默认 true），随派活 payload 传给插件；插件按会话记录该标志（随会话映射落盘）。
- 兜底：宿主版本不支持 hook 时，记录日志并在界面提示"该 OpenCode 版本无法自动处理权限弹窗"（不静默假装成功）。
- 普通会话完全不受影响；用户在自己会话里的权限弹窗照旧。

## 7. 可视化（动态效果）

- **节点链组件**（任务详情、创建弹窗、设置页共用一套）：
  - 当前节点：呼吸/脉冲光效（2.5s 周期、低幅度）；
  - 推进时：连接线上的流光（方向 = 推进方向）；
  - 完成：光效收束定格（一次 400ms 过渡）；
  - 失败：红光提示（低幅度，一次 1.5s）；
  - 「汇总中」：首节点回到脉冲态并标注"项目经理汇总中"。
- **状态语义由颜色 + 简短中文标签承载**，不用 emoji/符号徽标；动效只做注意力引导，不承载信息（去掉动效不丢信息）。
- `prefers-reduced-motion` 下全部退化为静态高亮/静止配色。
- 验收：UI gate 的双主题 a11y（含对比度）+ 视觉基线随新组件更新。

## 8. 兼容与迁移

- 旧任务：`meta.workflow_id` 指向旧预设的，继续按旧预设解析与推进；不受模板改动影响。
- 旧任务无 `working_dir`（meta 缺省 None）：**跟随宿主当前项目**（与旧行为一致）；新任务必填。
- 旧设置 `orchestration.workflow`（`opencode-only` 等）：保留读取用于旧任务兼容；**新建任务不再使用**（必须显式选模板，无默认）。
- `orchestration.notify_mode` 语义不变。
- 删除保护不再需要（无可删除的自定义工作流）。

## 9. 交付方式

- **一次性交付**（v2 修订，用户确认）：§2–§7 全部作为一个「集群功能 v1」实现（模型手填、工作目录下拉）；中间态不做验收，全部完成后打一个完整预览版验收一次。
- **后续**：模型下拉（从 OpenCode 拉取可用模型）、自定义提示词/信封模板的图形化编辑、模板导入导出。

## 10. 验收标准

- **单元/集成**：模板与节点配置合并解析；空 Agent → 明确报错且任务保持待开始；工作目录必填校验（创建与开始双校验）；项目列表读取（含库缺失/损坏的明确降级）；产出记录与截断；回流派活（含失败 blocked）；「重新发起」自动重派活；通知过滤（编排会话不建通知、普通会话不受影响）；插件权限 hook 仅对编排会话生效且尊重 unattended 标志；模型/目录透传（open 时 session.create 带 location+model、resume 时 switchModel）。
- **真机（微信）**：选「标准交付」模板并配置三节点（不同模型）→ 选工作目录（下拉）→ 建任务 → 开始执行 → OpenCode 会话落在指定目录 → 全程无选择框卡顿 → 中间节点无推送 → 只收到项目经理最终汇报 → 步骤条动态呈现每步状态与"汇总中"。

## 11. 已知后续项（非本期）

- Codex/CommandCode 等适配器"开新会话 + 指定模型"能力（多 Agent 模板重新开放的前提）。
- 首节点以外的节点是否允许人工介入（本期明确：不允许，中间节点不接触人）。
- verbose 模式系统进度文案的措辞细化（沿用现有 progress_body 文案）。
